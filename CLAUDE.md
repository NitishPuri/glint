# CLAUDE.md — glint

Context for Claude (and future me) working in this repo. Read this first, then `docs/PLAN.md`.

## What this is

A **learning sandbox for OpenGL and Vulkan side by side**. Every rendering technique is implemented
**twice** — once against raw OpenGL 4.6, once against raw Vulkan 1.3 — sharing only the non-GPU parts
(window, input, camera, asset loading, UI, scene parameters). The point is to *see* where the two APIs
differ, not to hide those differences.

It is **not** an engine. There is deliberately **no RHI / backend abstraction**. If you find yourself
writing `IBuffer`, `IDevice`, `CommandList` interfaces that both backends implement — stop. That is the
thing this project exists to avoid.

Success = for each technique, I can open `techniques/<name>/gl.cpp` and `vk.cpp` next to each other,
read `NOTES.md`, and understand every line and every difference.

## Owner / working style

- Owner: Nitish (graphics hobbyist, C++, comfortable with GL basics, learning Vulkan internals).
- AI writes a lot of the code; the owner reads, compares and tweaks. So:
  - **Code is for reading.** Prefer explicit, linear code over clever helpers. A `vk.cpp` that shows
    every `VkXxxCreateInfo` is better than one that hides it behind a builder — *until* that technique has
    been done raw once. Helpers are introduced only after the raw version exists in an earlier technique.
  - Comment the **why** and the **GL↔VK difference**, not the what. E.g.
    `// VK: clip-space Z is [0,1], GL is [-1,1] — hence camera.projection(aspect, ClipDepth::ZeroToOne)`.
  - Every technique ships a `NOTES.md` (see template in `docs/PLAN.md`), including a **Diagrams** section:
    mermaid for passes / resources / sync (renders on GitHub, Obsidian, VS Code with a mermaid extension), and
    matplotlib figures for anything quantitative or spatial, generated by `tools/diagrams.py` (venv:
    `python3 -m venv tools/.venv && tools/.venv/bin/pip install -r tools/requirements.txt`) into
    `techniques/<t>/diagrams/*.svg` — computed from the same formulas as the code, deterministic SVG, committed.
- Work in the phase order of `docs/PLAN.md`. Tick checkboxes there as things land. Don't jump ahead.
- **Learning path (Phases 8–15) heads towards GPU Gems.** Every technique's `NOTES.md` has a **Read** section:
  the GPU Gems chapter(s) (online link) and the local CD content in `/mnt/e/tree/graphics/nvidia/GPU-Gems`
  (`GPU-Gems-{1,2}-CD-Content/<Part>/<Chapter>`, `GPU-Gems-3-CD-Content/content/<NN>`) — code, shaders, assets and
  demos worth mining for implementation details (old D3D9/Cg/CUDA: read for the algorithm, don't port the API).
- The owner's Obsidian vault mirrors the plan: `1_TOPICS/Tech/Tech Projects/Glint - Learning Path.md` and one
  `Glint - Stage <N> - <name>.md` per phase (reading list + a Learnings section). When a technique lands, add its
  learnings there too (obsidian-kb skill) and tick its reading items.

## Build

```bash
source ~/vulkan-sdk/*/setup-env.sh           # glslc + validation layers
cmake --preset debug                          # GCC 14, Debug, into build/debug (also: release, clang-debug)
cmake --build --preset debug
./build/debug/glint_gl                        # OpenGL app
./build/debug/glint_vk                        # Vulkan app
```

`./build.sh [debug|release|clang-debug]` does the SDK sourcing + both steps. Configuring without a preset picks up
the system GCC 11 and fails the version check in `CMakeLists.txt` on purpose.

- CMake ≥ 3.22, Ninja. Dependencies are fetched with `FetchContent` (GLFW 3.4, GLM, ImGui, stb,
  tinyobjloader, tinygltf, VMA, doctest). **No prebuilt binaries in the repo**, no `ext/glfw-*.WIN64`.
- GL loader: glad2 generated for **GL 4.6 core** + `GL_KHR_debug`, vendored under `external/glad/`
  (generated once, committed).
- Shaders: GLSL `#version 460`. GL loads `.glsl` text at runtime (hot-reloadable). VK shaders are
  compiled to SPIR-V by `glslc` at build time into `build/<cfg>/shaders/`.
- From 12 on, shaders are **shared**: one `name.{vert,frag,comp}` for both APIs, `#include "glint.glsl"` for the
  `UBO/SAMPLER/IMAGE/PUSH_CONSTANTS/VERTEX_ID` macros, `#ifdef VULKAN` for real API differences. `*.gl.*` / `*.vk.*`
  files remain for techniques 01–11 (their per-API GLSL is part of the lesson).
- Large sample assets (glTF models) are downloaded at configure time into gitignored `assets/gltf/`
  (`cmake/assets.cmake`, SHA256-pinned); `-DGLINT_DOWNLOAD_ASSETS=OFF` skips that.
- Windows should keep working (MSVC + `find_package(Vulkan)`), but Linux is what's tested.

### Key rules

- `src/core/` must **never** include `glad`, `<vulkan/vulkan.h>`, or any GL/VK type. It produces CPU data
  (`MeshData{positions, normals, uvs, tangents, indices}`, `ImageData{w,h,channels,pixels}`) that each
  backend uploads its own way.
- A technique = shared `params.h` (a plain struct edited by an ImGui panel in `core/ui`) + `gl.cpp` + `vk.cpp`.
  Both apps show the same panel, so the same knobs exist on both sides.
- Each backend has its **own** technique interface (no common base across APIs):
  - `gl::Technique { init(); update(dt, Frame&); render(const Frame&); ui(); ~dtor }`
  - `vk::Technique { init(vk::Context&, VkFormat swapchainFormat); update(dt, Frame&); record(VkCommandBuffer, const vk::FrameInfo&); ui(); ~dtor }`
  - Both also have `setupCamera(Camera&)` (the technique's start/home camera).
  Registration is by name in each app, e.g. `GLINT_REGISTER_GL("08_shadow_mapping", ShadowMappingGL)`.
- GL and VK apps are **separate executables** (a GLFW window created for GL cannot get a Vulkan surface).
  A dual-window side-by-side mode is a later phase.
- Vulkan style: **Vulkan 1.3 core, dynamic rendering (`vkCmdBeginRendering`) + synchronization2**, no
  `VkRenderPass`/`VkFramebuffer` objects (render passes get one explicit NOTES.md entry explaining the
  legacy model). Memory: since 2026-10-27 `vk::Buffer`/`vk::Image` allocate through **VMA** (`docs/vma.md`);
  `--no-vma` gives the raw one-`vkAllocateMemory`-per-resource path. Raw allocation code inside a technique
  (01, 02, 16) stays raw on purpose: it's the lesson there.
- Clip-space conventions: VK asks the shared camera for `ClipDepth::ZeroToOne` (`glm::perspectiveRH_ZO`) and
  flips Y via negative viewport height (VK_KHR_maintenance1, core in 1.1), so the same camera code produces the
  same image. No global `GLM_FORCE_DEPTH_ZERO_TO_ONE`: it would change what `glm::perspective` means per
  translation unit. Documented in `docs/gl-vs-vk.md`.
- Validation must be **clean** (zero VK validation errors, zero GL debug errors of severity ≥ medium) before
  a technique is ticked done.

## Conventions

- C++23 (see below), `.clang-format` (Google, 2-space, 120 cols). Namespaces `glint`, `glint::gl`, `glint::vk`.
- Files: `snake_case.cpp/.h`. Types `PascalCase`, functions `camelCase`, members `m_camelCase`.
- Errors: `VK_CHECK(expr)` aborts with file/line + `string_VkResult`; GL errors come via `KHR_debug` callback.
- Logging: `glint::log::info/warn/error` on top of `std::format`. Every run also writes `logs/<app>_<date>_<time>.log`
  (gitignored) with a header (commit, build, args, config, GPU) and per-technique `summary` lines — compare
  those across runs for regressions. `--log FILE` / `--no-log-file` override.
- Commit per technique-backend (`techniques/05_vbo_indexing: vk`), small and reviewable.

## C++ standard

The project builds as **C++23** (`CMAKE_CXX_STANDARD 23`, extensions off) and requires GCC ≥ 14, Clang ≥ 19 or
MSVC ≥ 19.37 (`CMakeLists.txt` enforces it). **New and touched code uses the C++23 (and C++20) idiom where one
exists**, as long as it reads at least as clearly as the old form (code is for reading). Don't sweep untouched
files just to modernise them; convert the code you are editing. `clang-tidy`'s `modernize-*` checks flag most
of the old spellings (see [Tooling](#tooling)).

| Use | Instead of | Where it already is |
|---|---|---|
| `std::format`, `std::print`/`println` | `{fmt}`, `printf`, `iostream` | everywhere (`log.h`, app mains) |
| `std::expected<T, std::string>` for failures that are a normal outcome | throw + catch at the call site, `bool` + out-param | `gl::Program::build` (hot reload) |
| exceptions for failures that end the run | `std::expected` that every caller just rethrows | asset loaders, device creation |
| `std::views::zip(a, b)` | index loops over parallel arrays | `vk::Mesh`, `test_assets.cpp` |
| `std::views::enumerate(v)` | `for (size_t i...)` when `i` is only a label/second index | `11_gltf`, `gltf.cpp` |
| `range \| std::ranges::to<std::vector>()` | push_back loops that build a vector | `Registry::names`, `gltf.cpp` |
| `std::ranges::contains`, `find`, `sort` (with projections: `&Stage::path`) | hand-written search loops | `gl/shader.cpp` |
| `std::to_underlying(e)` | `int(e)` / `static_cast<int>(e)` on enums | ImGui radio buttons |
| `std::unreachable()` after a `switch` covering every enumerator | a dummy `return` (keep `-Wswitch` working) | `log.cpp` |
| `str.contains`, `starts_with`/`ends_with`, `map.contains` | `find(...) != npos`, `compare(pos, n, ...) == 0`, `find != end()` | `registry.h`, `gl/shader.cpp` |
| monadic `optional` (`and_then`, `transform`, `value_or`) | nested `if (opt)` chains | — |
| `0uz` | `size_t{0}` | — |
| deducing `this` (`this auto& self`) | const/non-const overload pairs, CRTP | — |

Leave the explicit form where the index *is* the lesson (prefix-sum levels, `for (k...)` over mip levels or
cascades), and in raw GL/VK sequences: `VkFooCreateInfo` filled field by field stays that way.

Not available yet on this toolchain (libstdc++ 14): `std::mdspan`, `std::flat_map`, formatting of ranges
(`std::format("{}", vec)`). When the compiler changes, re-probe with `<version>` feature-test macros
(`__cpp_lib_*`) and update this section; don't assume from release notes.

## Tooling

- **Presets** (`CMakePresets.json`): `debug`, `release` (GCC 14), `clang-debug` (Clang 20 + lld, build/clang-debug).
  Build `clang-debug` before committing larger changes: a second compiler finds different warnings.
- **clangd** (`.clangd`): reads `build/debug/compile_commands.json`; runs cheap clang-tidy checks as you type and
  flags unused/missing includes. Needs clangd ≥ 19 (`clangd-20`): clangd 18 can't parse libstdc++ 14's
  `<expected>` and reports false errors.
- **clang-tidy** (`.clang-tidy`): `modernize-*`, `bugprone-*`, `performance-*` + a few readability checks; the
  file explains each disabled check. Run on what you changed:
  `run-clang-tidy-20 -p build/debug -quiet 'src/|techniques/|tests/'` (whole tree) or
  `clang-tidy-20 -p build/debug <files>`. New code should be clean; fix or `// NOLINT(check)` with a reason.
- **Build-time profiling**: `cmake --preset clang-debug -DCMAKE_CXX_FLAGS=-ftime-trace`, then open the per-TU
  `.json` next to each `.o` in `chrome://tracing` / Perfetto (which headers make the NTFS build slow).
